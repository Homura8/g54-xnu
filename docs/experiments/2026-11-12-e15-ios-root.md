# E15: first iOS 16 root image on the G54

## Inputs and hypothesis

- Host preparation: `codex/ios-root-macos`, code commit `63ff9d8`.
- Connected phone: `cancunf`, XT2343-2, firmware 5-8-6, slot A,
  unlocked, bootloader Fastboot, no pending snapshot merge. Private source:
  `facts/20261112T173138Z-fastboot`; these fields were rechecked before flashing.
- Matching stock restore `boot.img` SHA-256:
  `e0fe4010a8a897e0b99253d4a51665582a850d6bb10837f535ebe3e0337cc2d4`.
- K2 from CI 43265320296, full SHA-256:
  `2bb9311a91e2c59552e961c2dcee4a916ee65a47bff024de6fcb9bdc543f43dc`.
- Probe: `UFS_FIX`, `LOADER_S=25`. Generated ADT includes `/sweet-ufs`
  and all 61 product properties from the supplied D22AP tree.
- Boot image SHA-256:
  `71f4d2c446d6a1623497c56dbeec39df7a78b33f5cb1d32e8aec513547bc87e4`.
- Raw root SHA-256:
  `c549420151e9ad4e342619b9c97dd91340def600f0eb4bf8d8b08442188b6b95`.
- Android sparse root SHA-256:
  `d8af10d8a59f6729ad5c83c3db838a13b50385f960e72c128ac10259c515ba90`.

Hypothesis: E14's working UFS path can mount the real HFS+ iOS root in
`userdata` and start Apple's launchd. This is the first G54 userspace-root
test; host image checks alone do not establish userspace execution.

Boot arguments:

```text
debug=0xc serial=3 cpus=1 keepsyms=1 -noprogress rd=ufsroot0
ufsrw=1 rootrw=1 launchd_unsecure_cache=1 unentitled_ios_sim_launch=1
ignition_level=1 wdt=-1 wdt_test=no_user_checkin g54panicreset=45
```

## Host observations

The owner ran the privileged macOS builder in Terminal. The completed image
is a 16 GiB case-sensitive journaled HFS+ volume with about 11 GiB used;
both fsck passes reported OK. Read-only inspection verified iOS 16.7.16
(20H392), arm64 launchd/dyld owned root:wheel with mode 0755, 44 matching
shared-cache hardlinks, the bring-up launchd changes and SpringBoard's
executable.

The first raw-image `fastboot flash userdata` stopped with
`Failed reading from userdata` before a transfer began. AOSP's
[copy_avb_footer implementation](https://android.googlesource.com/platform/system/core/+/refs/heads/main/fastboot/fastboot.cpp)
reads raw images into a string, but skips this handling for sparse images.
Converted with upstream `anestisb/android-simg2img` at
`a6fcc0f1c61b2aa5b55516829cd7d13dbfbacb91`, built locally in ignored `out/`.
An upstream `simg2img` reconstruction compared byte-for-byte equal to the
validated raw image before retrying.

## Device result

At 17:51 UTC, `fastboot -S 256M flash userdata out/root/ios16-root.simg`
began transferring and writing 45 chunks. All 45 transfers and writes
returned OKAY; total 383.684 seconds. The boot image was then flashed to
`boot_a` successfully (1.864 seconds), and `fastboot reboot` returned OKAY
at 17:58:35 UTC.

### Owner photographs: root and real iOS userspace confirmed

Private owner photographs `IMG_4316.jpeg`–`IMG_4325.jpeg` show:

- Probe: vendor reset, link startup RC 0, peer power mode `0x55`, NOP IN
  and `fDeviceInit` complete, then the SWEETXNU handoff.
- `SWEET CPU: 1/1 CPUs initialized, SGI1 verified`.
- `userdata` on LUN 2, read-write, root device `ufsroot0`;
  HFS creates its hotfile btree on `iOSRoot`.
- `/dev/ufsroot0 on / (hfs, local, journaled, noatime)`.
- Apple's launchd logs its version, PID 1, the expected boot arguments,
  boot tasks and `Early boot complete. Continuing system boot.`
- Usermanagerd creates and saves the mobile user session; keybagd loads
  the system keybag; corecrypto's userspace FIPS POST reports all tests passed.
- `exec SpringBoard`, followed by more xpcproxy executions.

**M4 (root + real launchd) is observed. SpringBoard exec is observed, but
successful SpringBoard initialization and a graphical interface are not.**
The owner reports a very slow boot and no GUI. Launchd's visible relative
timestamps reach about 4:33 at its startup and 6:37 at early-boot completion;
these are observations, not a measured CPU-versus-I/O breakdown.

Warnings include shared-cache `not in trust cache`, missing optional bindfs
paths/data volume, `GetMasterBlock` EBUSY, unsupported HFS data protection and
resource-violation messages. Boot proceeds beyond these in the photos.
Pinned topaz's NOTES also records the cache warnings and GetMasterBlock EBUSY
as nonfatal in this bring-up configuration. None of these photos identifies
the specific GUI blocker; obtain process samples before changing userland.

The root image on the phone has now been modified by writable iOS boots.
Do not use the original host image as an OLD baseline for a sparse diff.

Recovery remains the matched stock `boot_a` image and an Android userdata
reset. Slot B and all critical partitions are outside this experiment.
