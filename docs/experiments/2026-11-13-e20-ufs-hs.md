# E20: UFS back to HS (fast) mode, with E19's console mute

## Why

E18 reached the Apple logo and, after 30+ minutes, the iOS lock screen. The
console then covered it (owner report, 13 November). The probe screens
explain the speed. LK ran UFS in FAST mode (E8: `PA_PWRMODE 0x11`). After the
probe's device reset and link startup (E13/E14), the link runs in PWM
slow-auto (peer `0x55`), and every iOS read pays for that.

## One image, two orthogonal changes (deliberate)

Each iOS boot now costs ~30 minutes, so E20 combines:

1. E19's `sweetfb_noconsole=1` (display only: ordinary console text stops
   drawing over presented frames; panics still draw), and
2. probe `-D UFS_HS` (storage only): after `fDeviceInit`, gear = min(local,
   peer `PA_MAXRXHSGEAR`), rate B, terminations, all connected lanes, Linux's
   default DL timeouts (`PA_PWRMODEUSERDATA0-5`, `DME_Local*TimeOutVal`), then
   `PA_PWRMODE = 0x11` and wait for `IS.UPMS`. This follows Linux
   `ufshcd_change_power_mode()`. MediaTek's PMC-via-FASTAUTO path applies only
   to HS-G4+.

The probe screen shows the storage result directly (`HS …`, `PMC …`), and
boot time and the panel show the display result, so the two remain separable.

## Result

**PASS on both changes (owner photos and report, 13 November 2026).**

- Probe: `HS MAX L=3 P=3 GEAR=3 LN=22`, then `PMC SET=00 RC=00 UPMCRS=1 PWR
  L=11 P=11 TXG=3`. Host and the Samsung UFS (KM8V9001JM) both support
  HS-G3 on 2+2 lanes, and the link is now FAST/FAST gear 3 (E13–E19 ran
  PWM slow-auto `0x55`).
- Owner: "significantly faster": Apple logo, then briefly a garbled copy
  of the probe screen, then **the iOS lock screen in about 2–3 minutes**
  (E18: 30+ minutes).
- Lock screen photographed twice, a minute apart: "Wednesday, December 31",
  4:02 then 4:03 (the clock advances; no RTC yet), the charging battery
  icon, the camera button and the home indicator, with no console text
  over it. Ruby's magenta corner and green centre squares are its
  deliberate debug markers.
- The garbled screen is the probe's own text in OVL1 layer 0 (`BUF 1 AT
  FE0D0000 P 1100`), shown briefly at the wrong pitch while iOS's
  presentation takes over. Cosmetic; the probe should draw only into the
  visible layer.
- Touch, power and volume keys do nothing: no G54 input driver exists yet
  (ruby's are MT6877-specific and gated off).

Success criteria: `PMC … UPMCRS=1`, `PWR L=11 P=11`, XNU still finds
`userdata`, and a markedly shorter boot. If the PMC fails, XNU should still
boot in PWM (link left as before) or panic and return to Fastboot.
