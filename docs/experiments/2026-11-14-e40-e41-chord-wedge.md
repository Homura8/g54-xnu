## E40 log tail (decayed text corrected only where the format string is known)

```
SWEET HID: touch 0 down at 3,1310 edge
SWEET HID: touch 0 up at 0,0 edge
G54 KEYS: key … down
SWEET HID: key 0xe9 down (1 clients)        volume up
G54 KEYS: key … down
SWEET HID: key 0x30 down (1 clients)        power
SWEET AKS: SpringBoard sel 13 / 17 / 1 / 16 / 17 …
SMP --- sample 0
SMP SpringBoard[…] slide 0xfb8c000 …
SMP SpringBoard t0 … t3 pc/lr/sp/bt …        (log ends)
```

- No key **up** events, although the keys were released after ~3 s, and
  nothing from the later Power + Volume Down hold, which E29 showed is
  normally logged. `SWEET HID: key …` is printed for every event, just
  before `dispatchEvent()`; 0203's own `G54 KEYS: key %d down` is limited to
  6 presses.
- The key thread (0203) has only bounded waits (2 ms SPMI timeouts, 20 ms
  sleep). Its unbounded step is `sweet_hid_key()` → `SweetHIDButtons::key`
  → `IOHIDEventService::dispatchEvent` (no lock held) → the user client's
  `_commandGate->runAction(enqueueEventGated)`, which waits for that
  client's work-loop gate (shared with backboardd's `externalMethod`
  calls). Hypothesis: the key thread blocks there after the power-down
  event.
- The sampler holds SpringBoard's `task_lock` across `vm_map_read_user()`
  (a deadlock risk in itself), but E41 shows it is not the cause of #14.

## Not established

Where exactly the key thread (or backboardd) blocks; whether the PMIC
countdown from the unacknowledged power press (E30/E31) explains E41's cold
reset and E40's decay (if the key thread is stuck, nothing acks the PMIC).
A cheap check: wedge it, unplug USB, wait ~2 min; a self power-off would
confirm the key thread is stuck.
