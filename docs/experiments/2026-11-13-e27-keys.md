# E27: G54 side keys read live (probe -D KEY_SCAN)

| Field | Observation |
| --- | --- |
| UTC date | 2026-11-13, flashed and rebooted 03:58:09 |
| Image | `out/g4/e27-keys-boot.img`, SHA-256 `1fee25d4a49166b7c28d3d0e301da0e5747bef42adecdc80e9a238318f7295d1`; XNU payload and cmdline identical to E26 (K3, `g54nvt=1`); probe `-D UFS_FIX -D UFS_HS -D TOUCH_SPI -D TOUCH_FW -D KEY_SCAN -D NO_RESV -D LOADER_S=5` (SHA-256 `4a054034…516d`) |
| Hardware map (sources) | Base DTB (vendor_boot): `kp@1c00e000` "mediatek,kp"; MT6363 at SPMI slave 4 with `mediatek,mt6363-keys` (power 0x74, home 0x72). DTBO overrides KPD `hw-init-map` key 0 = 0x73 (KEY_VOLUMEUP), `sw-pwrkey` 0x74, `sw-rstkey` 0x72 (KEY_VOLUMEDOWN on the PMIC home key). Stock `mtk-pmic-keys.ko` `mt6363_regs`: TOPSTATUS **0x1e**, power bit 1, home bit 3. Stock `spmi-mtk-pmif.ko` (`mediatek,mt6855-spmi` → MT6879-family table): SWINF0 ACC 0x800, WDATA 0x804, RDATA 0x814, VLD_CLR 0x824, STA 0x828, channels every 0x40; the AP uses SWINF 2 (see Channel) |
| Observation (owner photo and report) | `SWINF STA 8441 8441 8441 8441` (all idle), **`PMIC CH=0 RC=00 TOP=0000001E`** at rest; pressing the buttons showed **POWER, VDOWN and VUP** (labels accumulate on screen; `KP=FBFE` while volume up was held). Owner: "all three worked successfully" |
| Result | **PASS: all three keys readable. Volume up = KPD KP_MEM1 bit 0 (0 = pressed); power = TOPSTATUS bit 1, volume down = TOPSTATUS bit 3 (active-low, idle 0x1e); SPMI software channel 0 works from EL1.** |
| **Resets after key presses** | After the KEY_SCAN boot in which the buttons were pressed, the phone **reset itself during the iOS boot, before the lock screen** (owner, ~04:05 UTC), landing in a normal boot rather than Fastboot: a reset below XNU (the loader routes XNU resets/panics to Fastboot; NONRST2 lost). **A later boot of the same E27 image with no button presses booted fully** (owner, ~04:10 UTC), although the probe again polled TOPSTATUS through SWINF 0 at 50 Hz for 25 s. So the SPMI reads alone did not cause it; the **key presses** are the common factor, matching the owner's earlier report that the E18/E21 restarts followed button presses and stopped when the buttons were left alone. Mechanism unknown: candidates are an unserviced MT6363 key interrupt/long-press state (stock `mt6363_regs` also lists 0x90f, 0xa0e, 0xa0f, which `mtk-pmic-keys` programs for long-press reset) or another firmware agent reacting to the keys |
| Touch after KEY_SCAN | Boots of E27 had **no touch in iOS**, although the kernel (K3) and the firmware download are identical to E26. Reboot from Fastboot at 04:12:17 UTC with no key presses: the probe touch test worked (owner drew "Hi"; `ERR=003F`, `BOOT ST=A1`), the KEYS screen timed out untouched, and touch still did not work on the iOS lock screen. So touch is lost **after** the probe's touch test; the only new step after it is the KEY_SCAN loop (SPMI reads through SWINF 0 at 50 Hz for 25 s) plus 25 s of delay. Leading hypothesis: using another master's SWINF disturbed its PMIC traffic (e.g. a touch supply); not proven |
| Channel | Independently, the stock `mtk_spmi_probe` selects the AP's software channel as `regs[25 + 5 * soc_chan]` with **soc_chan = 2** for `mediatek,mt6855-spmi` (pmif data word +0x2c): the AP owns **SWINF 2 (PMIF+0x880)**, not SWINF 0. Probe KEY_SCAN and kernel 0203 now use SWINF 2 only |
| Next | Kernel patch 0203 (`g54keys=1`, SWINF 2). E28 tests it in iOS; if key presses still reset the phone, decode the MT6363 long-press/interrupt registers (0x90f, 0xa0e, 0xa0f) from the stock driver before going further |
