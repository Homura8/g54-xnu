| Run | Change | Observation | Conclusion |

| E11 | Linux SiP `0xc2000276` DEVICE_RESET low/high, with the host still enabled | both calls return 0; startup still RC 1 | reset alone is not enough |

| **E13** | **vendor order**: HCE=0 → `0xc2000276` reset low ≥10 µs → high → 15 ms → HCE=1 → `DME_SET` `VS_UNIPROPOWERDOWNCONTROL(0xd0a8)=0`, `PA_LOCAL_TX_LCC_ENABLE(0x155e)=0`, `VS_SAVEPOWERCONTROL(0xd0a6)` bit 6 clear → `DME_LINKSTARTUP` | `VS PWRDN=0 SAVEPWR=0x90`; reset/HCE OK; **startup RC 0; peer PA_PWRMODE 0x55 (slow-auto)**. XNU: `SWEET UFS: command 0x00 failed: ocs 0x0 upiu 0x21 response 0x1 status 0x2` ×3 (a real SCSI CHECK CONDITION), panic errno 5 | **link up**. The reset device still needs `fDeviceInit` (E14) |

**LK 5-8-6 teardown (disassembly of `platform/mediatek/common/ufs/ufs_interface.c`):**
before jumping to the kernel LK sends the UFS power-off notification
(`ufs_poweroff_notify`, three tries), then calls `smc(0xc200040d, 0x10, 1)`
and `smc(0xc200040d, 2 /* DEVICE_RESET */, 0)`; its platform-mode getter
(`0x41f0`) is the constant 2, so this path is always taken. **The UFS
device is left held in reset.** Ruby's MT6877 LK does not do this.
The vendor sequence follows MediaTek's `ufs-mediatek.c` (kernel_device_modules-5.15:
`ufs_mtk_device_reset`, `ufs_mtk_hce_enable_notify`, `ufs_mtk_pre_link`).
The stock DTB has no `phys`/`va09-supply`, so no M-PHY/VA09 steps are needed.
