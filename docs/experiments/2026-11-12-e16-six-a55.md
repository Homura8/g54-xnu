# E16: six Cortex-A55 cores

Hypothesis: the existing pinned K2 PSCI/SMP path can start the G54's six
A55s, reducing single-CPU contention during iOS boot.

## Inputs and checks

- Firmware 5-8-6, slot A, unlocked, bootloader Fastboot;
  `snapshot-update-status=none`, rechecked live before the flash.
- K2 kernel unchanged from E15 (CI 43265320296), SHA-256
  `2bb9311a91e2c59552e961c2dcee4a916ee65a47bff024de6fcb9bdc543f43dc`.
- Probe and ADT byte-identical to E15. The complete uncompressed SWEETXNU
  payload compares equal to E15 after replacing only `cpus=1` with `cpus=6`.
- Experimental boot SHA-256:
  `694380991abe01e1943146f7c81b9ab115c12cdc4251e38f6985fdd83d8a88d2`.
- Stock restore boot SHA-256:
  `e0fe4010a8a897e0b99253d4a51665582a850d6bb10837f535ebe3e0337cc2d4`.
- Root is the writable E15 iOS root, with its first-boot state retained.
  This is also a warm boot, so elapsed-time differences cannot be attributed
  solely to CPU count.

Pinned topaz patches 0065/0078 implement PSCI CPU_ON through SMC and verify
each selected CPU with SGI1. The G54 ADT already supplies the observed
MPIDR affinities `0x000`–`0x500`. A78 cores are not described or tested.

## Result

`fastboot flash boot_a out/g4/e16-smp-boot.img` completed OKAY in 1.987 s.
Reboot issued at **18:11:16 UTC, 12 November 2026**.

The owner explicitly reported **"6/6 CPUs verified, its still progressing
through boot"**, in response to checking
`6/6 CPUs initialized, SGI1 verified`.
Six-A55 startup is therefore owner-observed. Subsequent owner photos
`IMG_4330.jpeg`–`IMG_4335.jpeg` show `exec SpringBoard`, `exec backboardd`
and further daemon launches. The owner reports that boot is still very slow
but faster than E15. This is a qualitative observation, with the warm-root
confound above; no measured speed-up or GUI is established.

### Process samples and warning flood

The photos show one main thread for each UI process, with the same saved
PC/backtrace. Shared-cache slide is `0x4a4b0000`; subtracting it maps the
addresses into `/usr/lib/dyld`. The root image's standalone dyld has matching
instruction bytes and symbols, giving this chain (offsets relative to dyld):

| Offset | Symbol |
| --- | --- |
| `0x3d08` | `dyld3::MachOFile::forEachSection + 0x34` |
| `0x517b4` | `dyld3::MachOFile::forEachDOFSection + 0x44` |
| `0x1e1d8` | `dyld4::RuntimeState::notifyDtrace + 0x10c` |
| `0x15b3c` | `dyld4::prepare + 0x4a8` |
| `0x142e0` | `start + 0x6e0` |

These samples place both processes in dyld's library-section scan before
normal application startup. A saved user PC can also represent a thread
waiting on a page fault; this does not establish a CPU spin or deadlock.
In particular, it does not identify ruby's later ICL/MobileGestalt deadlock,
so that userland patch has not been applied. The observed PWM slow-auto UFS
link remains a plausible loading bottleneck, not a measured cause.

Repeated `send_resource_violation(CPU wakes, ...): error 0x10000004`
messages dominate later output (E15 showed `0x10000003`). These are
`MACH_SEND_TIMED_OUT` and `MACH_SEND_INVALID_DEST`, respectively. In the
pinned Apple XNU source, `send_resource_violation` sends to the host's
resource-notification port with queue-limit handling. A timeout code alone
does not establish a long blocking wait. The default wakeup monitor can be
disabled using the existing `task_wakeups_monitor_rate=0` boot argument;
[E17](2026-11-12-e17-wakeup-monitor.md) tests that single change.

Rollback: flash E15's single-core image or the matching stock boot image
to `boot_a`. Android additionally requires userdata reset. No userdata,
slot-switch, bootloader or critical-partition write was performed by E16.
