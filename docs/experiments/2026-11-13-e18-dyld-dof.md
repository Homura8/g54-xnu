# E18: skip dyld's DTrace section scan

## Hypothesis and control

E16 sampled the main threads of both SpringBoard and backboardd in
`dyld3::MachOFile::forEachSection`, called by `notifyDtrace` during dyld
startup. E17 suppressed the CPU-wakeup warning flood, but the owner still
reported slow boot and no interface after leaving the phone running.

E18 adds **only `dtrace_dof_mode=0`** to E17's boot arguments. The hypothesis
is that avoiding the sampled section scan reduces startup work and lets the
UI processes advance. Neither a speed-up nor a GUI is assumed in advance.

Apple's pinned XNU source defines
[`DTRACE_DOF_MODE_NEVER` as 0](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.141.3/bsd/sys/dtrace_impl.h).
Its [dtrace initialization](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.141.3/bsd/dev/dtrace/dtrace.c)
parses `dtrace_dof_mode`, defaults to lazy registration for macOS and never
for other targets, and enables the commpage DOF flag only outside NEVER mode.
The reused SWEET configuration is based on `MASTER.arm64.MacOSX`.
The closest public dyld source, version 1066.10 (the supplied image is 1067),
reads that [commpage flag](https://github.com/apple-oss-distributions/dyld/blob/dyld-1066.10/dyld/DyldDelegates.cpp)
before [scanning sections in notifyDtrace](https://github.com/apple-oss-distributions/dyld/blob/dyld-1066.10/dyld/DyldRuntimeState.cpp).
E16's actual binary symbols establish the photographed stack independently
of this source-version difference.

SpringBoard/backboardd samples if none appears after roughly five minutes.

still prevents an interface. Repeated fairplayd.H2/bluetoothd exec lines
alone do not identify either service's exit reason or the UI blocker.
