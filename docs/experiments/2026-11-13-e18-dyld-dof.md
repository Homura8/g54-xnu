# E18: skip dyld's DTrace section scan

## Hypothesis and control

E16 sampled the main threads of both SpringBoard and backboardd in
`dyld3::MachOFile::forEachSection`, called by `notifyDtrace` during dyld
startup. E17 suppressed the CPU-wakeup warning flood, but the owner still
reported slow boot and no interface after leaving the phone running.

E18 adds **only `dtrace_dof_mode=0`** to E17's boot arguments. The hypothesis
is that avoiding the sampled section scan reduces startup work and lets the
UI processes advance. Neither a speed-up nor a GUI is assumed in advance.

Apple's pinned XNU source defines
[`DTRACE_DOF_MODE_NEVER` as 0](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.141.3/bsd/sys/dtrace_impl.h).
Its [dtrace initialization](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.141.3/bsd/dev/dtrace/dtrace.c)
parses `dtrace_dof_mode`, defaults to lazy registration for macOS and never
for other targets, and enables the commpage DOF flag only outside NEVER mode.
The reused SWEET configuration is based on `MASTER.arm64.MacOSX`.
The closest public dyld source, version 1066.10 (the supplied image is 1067),
reads that [commpage flag](https://github.com/apple-oss-distributions/dyld/blob/dyld-1066.10/dyld/DyldDelegates.cpp)
before [scanning sections in notifyDtrace](https://github.com/apple-oss-distributions/dyld/blob/dyld-1066.10/dyld/DyldRuntimeState.cpp).
E16's actual binary symbols establish the photographed stack independently
of this source-version difference.

## Result: first graphical iOS output on the G54

**The owner photographed an Apple logo on the panel**, with accompanying
`SWEET FB DBG` output for layer 0, IOSurface IDs 2 and 3, a 1080×2400
copy and destination PA `0xfeac6000`. The source and destination centre
pixels are white, while their first pixels are black. This establishes
iOS-produced surface content reaching the G54 panel through the existing
IOSurface/IOMFB CPU-copy path. It is more than an `exec SpringBoard` line,
but **a lock/home screen and interactive GUI remain unobserved**.
The magenta corner and green centre squares are display diagnostics.

The first logo photos were received by **02:04:57 UTC, 13 November**,
24 min 18 s after the host issued reboot. This is an observation bound,
not a precisely measured time to first frame. There was no further flash,
reboot or host-side input change during this boot. The root is writable
and retains earlier boot state, so a controlled cold-root speed comparison
has not been performed and the improvement cannot be assigned solely to
the new boot argument.

### UI-process progression

Owner photos before and after the logo retain SpringBoard PID 26,
backboardd PID 56 and cache slide `0x0d038000`. Read-only symbolication
uses this root's actual shared cache, its local symbols and export tries;
the backboardd entry point is independently checked against `LC_MAIN`.
Raw photos, OCR and register dumps remain private and uncommitted.

| Observation | Decoded location / behaviour |
| --- | --- |
| Early SpringBoard sample | dyld `hasThreadLocalVariables`, called from `RuntimeState::initialize` during libSystem initialization |
| Sample 2 | both UI main threads in libobjc image registration (`map_images_nolock`) |
| Sample 3 | backboardd at its executable entry point + `0x2c`; SpringBoard in `load_categories_nolock`, called through dyld `notifyObjCInit` |
| Sample 5 | SpringBoard waits synchronously in `BKSDisplayGetMainScreenInfo` during `BKSSystemShellService` setup; backboardd waits for a MobileGestalt-related XPC reply from `AWScheduler` initialization |
| Later input setup | backboardd successfully opens `SweetHIDTouch` through `IOHIDEventServiceUserClient`, and opens AppleKeyStore; this does not prove physical G54 touch events |
| Sample 7, before logo | backboardd in `PUIProgressWindow` image/layer creation, enumerating bundle resources with `readdir`; SpringBoard still waits for main-screen information |
| After logo | SpringBoard reaches `initializeSystemServicesBeforeApplicationDidFinishLaunching`, including Control Center repository initialization; its saved PC is in `lstat64` |
| Later Control Center loading | SpringBoard enumerates bundle metadata in `CCSModuleRepository::_queue_loadAllModuleMetadata`; `readdir` / CoreFoundation bundle inspection appears on its main stack |
| Sample 9 | backboardd loads an NSBundle, resolving filesystem paths with `lstat64` |
| Subsequent samples | backboardd's main thread reaches `CFRunLoopRunSpecific`; SpringBoard's main thread waits synchronously for user cfprefsd in `CFPrefsSearchListSource` |

These observations establish movement beyond E16's DTrace scan. They do
not show a fixed dyld stall or the known upstream ICL/MobileGestalt
deadlock, and that userland patch remains unapplied. Filesystem activity
and slow resource loading are visible in samples; neither CPU utilization
nor storage throughput is measured by those snapshots.

The owner also photographed rapid repeated backboardd lookups for
`IOAcceleratorES`, each returning zero matches. This is repeated service
discovery, not evidence of repeated process restarts. The logo appeared
later in the same boot: absence of that accelerator did not prevent the
observed CPU-copy output. Duplicate Objective-C game-controller plug-in
class warnings likewise precede successful touch-service setup and the
logo; they are not yet a demonstrated GUI blocker.

The owner subsequently saw the logo disappear and reappear while more
samples and daemon activity were printed. The same UI PIDs remain in
the samples. This does not establish a reboot or UI-process crash; console
clears/overlays and frame presentation remain possible explanations.

### Old probe graphics reappear, distorted

Later owner photos show the green/white pre-XNU `G54 PROBE V4` information
screen reappearing with horizontal skew/overlap, while readable, fresh iOS
logs continue over it. The surrounding samples retain SpringBoard PID 26,
backboardd PID 56 and the same cache slide. No new boot sequence, panic or
UI-process crash is captured. This is a **display-presentation symptom**;
it does not establish that the probe ran again. Stale framebuffer contents,
surface layout and the console sharing scanout memory are candidates, not
yet a demonstrated root cause.

Inspection of the actual K2 recipe confirms that ruby's historical
`0081-ruby-swap-debug.patch` is included; the later topaz direct-scanout and
double-buffer patches are excluded. The existing framebuffer maps the
physical panel as a default IOSurface and copies other surfaces into it.
It keeps the kernel console active by default, crops the presented
1125×2436 coordinates to the native 1080×2400 panel, and deliberately draws
the magenta/green squares. These source facts explain diagnostic overlays,
but do not by themselves explain the distorted old probe image.

The many `SWEET AKS ... sel 17 ... -> 0x0` lines are separate key-store
user-client diagnostics, not the CPU-wakeup warnings disabled in E17.
SpringBoard's sampled preferences wait is a new location; one snapshot does
not establish a cfprefsd deadlock. A read-only host presence check at
02:15 UTC found no ADB or Fastboot device, as expected while this build runs
without a USB command channel; no reboot or write was issued.

An [E19 console-isolation image](2026-11-13-e19-console-isolation.md) is
prepared locally for a later bounded test. **It has not been flashed.**
Keep E18 running while the owner observes continued progress.

### A separate, identified process kill

One photo explicitly records `driverkitd[66]` killed with signal 9 and
exit-reason namespace 1, code `0x7`. In the exact XNU headers,
[namespace 1 is `OS_REASON_JETSAM`](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.141.3/bsd/sys/reason.h)
and [code 7 is `JETSAM_REASON_MEMORY_PERPROCESSLIMIT`](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.141.3/bsd/sys/kern_memorystatus.h).
This establishes a per-process memory-limit kill for driverkitd, not global
RAM exhaustion or the cause of the other services' relaunches. No such kill
of SpringBoard/backboardd is captured in these photos. A logd privilege-1002
denial is also visible; its effect has not been established.
